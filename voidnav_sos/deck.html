01 · The problem

After a disaster, the first thing everyone wants is to talk.
That's exactly when the network disappears.

Pain 1

No way to ask for help

Survivors can't request rescue, medical aid, food or water, or tell family they're safe.

Pain 2

Location is unknown

Even when a message gets out, responders don't know which area it came from.

Pain 3

Emergency networks jam

If every message is rebroadcast by every relay, a small radio channel chokes exactly when traffic peaks.

We need a communication path that works with zero infrastructure, is simple for a panicked person, tells the sender their message arrived, and stays fast even when hundreds of people use it at once.

03 · The SOS node

A device anyone can use in a panic

Question flow

Answers become numbers: the whole request fits in about 21 bytes.

Optional · phone link

Join the node's Wi-Fi, a local page opens, type a short message (≤ 40 chars) for an SOS station or another person's node. No internet, no app.

Location

Fixed public nodes: exact coordinates saved at installation. Portable nodes: GPS module. The dashboard always says which one it is: node location, not the survivor's exact spot.

Two lights, two meanings

Orange = sent by this node. Green = an SOS operator has read it and assigned help. The screen also shows "Delivered" as soon as the station's automatic receipt arrives.

04 · The network · our core engineering

Fast for urgent cases, never jammed

LoRa doesn't create a mesh by itself. We wrote the forwarding rules; these six stop the channel from choking.

1 · Forget repeats

Every message has a unique ID. Relays remember recent IDs and drop copies.

2 · Hop limit + expiry

Max 4 hops and a lifetime (10–30 min), so nothing circulates forever.

3 · Closer-only forwarding

A relay forwards only if it is nearer the station than the sender. No blind flooding.

4 · Priority lanes

P0 rescue/medical → P1 vulnerable → P2 food/water → P3 "I'm safe". Waiting messages move up a lane so none starve.

5 · Listen, then talk

Check the channel, wait a short random time (shorter for P0), and cancel if another relay already forwarded it.

6 · Capped retries

No receipt? Retry with growing gaps, max 5 for P0 and 2 for P3, reusing the same ID.

Both modules must be the same frequency band, with antennas fitted before any transmission.

Demo script
  1. Serial menu acts as the node screen: pick "Need rescue", answer Y/N/Maybe
  2. LoRa A sends the 21-byte packet over the air; orange lights
  3. LoRa B receives it, decodes it, and the dashboard pin appears
  4. Click "Mark read"; B sends it back; A receives it; green lights
  5. Send the same ID twice: the duplicate is dropped; P0 jumps ahead of P3 in the queue

Honest scope: one ESP32 drives both radios, so this proves the packet, receipt, LED, priority and duplicate logic over a real radio link. A true multi-hop relay chain needs 1 ESP32 + 1 LoRa per node (≥ 3 boards); that's our next build step.

08 · Do we need quantum?

Not for the radio link, but it can plan where relays go

Where quantum doesn't belong

Sending SOS packets, relaying, receipts, LEDs: this all runs on cheap microcontrollers in milliseconds. Adding quantum here would add cost and nothing else. The core system is fully classical.

Where it fits: planning before a disaster

With a limited number of relays, where you put them decides how many people stay connected. That's a "choose K of N sites" optimisation that grows explosively with map size. We formulate it as a QUBO and solve it with QAOA on Qiskit, as an offline planning tool.
